## 1. Контекст и Проблема (Зачем?)

В Казахстане ежегодно выпускается более 150 тысяч абитуриентов. Существующие порталы часто страдают от двух проблем:

1. **Информационный хаос:** Данные о проходных баллах, грантах и профильных предметах разбросаны по разным PDF-отчетам и не всегда актуальны.

2. **Технологическая отсталость:** В моменты пиковых нагрузок (июль-август, когда идет подача заявок) государственные и частные ресурсы часто «ложатся» или работают крайне медленно.

**Цель проекта:** Создать отказоустойчивый API и удобную систему управления данными, используя «промышленный» стек, который позволит выдерживать огромные наплывы юзеров на минимальном железе.

---

## 2. Целевые данные (Что храним?)

Проект оперирует сложной сетью связей, которые идеально ложатся на **графовую модель**:

- **Вузы (University):** Название (RU/KZ/EN), локация, тип (гос/частный), описание, контакты, ссылки, фото (хранятся в MinIO).

- **Специальности (Specialty):** Код (например, `6B06101`), название, описание области.

- **Предметы ЕНТ (Subject):** Математика, Физика, Биология и т.д.

- **Связи (The Core):**
  - **Offers (Вуз -> Специальность):** Здесь хранятся динамические данные: количество грантов (общие, сельская квота), стоимость обучения, минимальный балл, проходной балл прошлого года.

  - **Requires (Группа ОП -> Предметы):** Пара профильных предметов ЕНТ, необходимых для поступления.

## 3. Архитектурная парадигма: Data-as-Code

### Ключевое решение v2.0

Мы полностью отказались от веб-админки (HTMX + SSR + Google OAuth) в пользу паттерна **Data-as-Code**:

- **Данные** о вузах, специальностях и группах ОП хранятся как структурированные `.yml` и `.md` файлы в отдельном Git-репозитории.
- **Бэкенд** — тонкая API-прослойка между клиентскими приложениями и графовой базой данных, отвечает за роутинг и обход графов.
- **Синхронизация** — изменения в Git доставляются в SurrealDB через webhook / GitOps pipeline.

### Почему Data-as-Code, а не админка?

| Проблема классической админки          | Решение через Data-as-Code                        |
| -------------------------------------- | ------------------------------------------------- |
| Вектор атаки: OAuth, сессии, CSRF, XSS | Отсечён полностью — нет веб-интерфейса управления |
| Нужен сервер для CRUD                  | Данные редактируются в Git (PR → review → merge)  |
| Дублирование валидации (клиент+сервер) | Валидация через JSON Schema + CI                  |
| Затраты мощностей на SSR-админку       | Бэкенд обслуживает только read-only API           |
| Сложность аудита изменений             | Полная история в git log                          |
| Откат ошибочных данных                 | `git revert <sha>` → webhook → БД обновлена       |

## 4. Технологическая часть (Как?)

### Backend: Go (Golang) — тонкая API-прослойка

Бэкенд не содержит бизнес-логики управления данными — он лишь маршрутизирует запросы и обходит граф.

- **Роутинг:** 8 read-only JSON API endpoints (список вузов, детали вуза с графовым обходом, группы ОП, специальности, предметы ЕНТ).
- **Графовые запросы:** Обход связей `university → offers → specialty → group → specialty_group → requires → subject` средствами SurrealDB.
- **Webhook:** Приём push-событий из Git, валидация подписи (HMAC-SHA256), синхронизация данных в SurrealDB.
- **Embed:** Миграции (`schema.surql`) вшиваются в бинарник через `embed.FS`. Деплой — один файл.

### Database: SurrealDB

Наше секретное оружие. Она заменяет нам сразу три базы:

1. **Graph:** Мы не используем `JOIN`, мы идем по графу `university->offers->specialty`, что в разы быстрее на сложных выборках.

2. **Document:** Мы храним профиль вуза как JSON-документ со схематичной гибкостью.

3. **Search:** Встроенный полнотекстовый поиск позволяет абитуриенту найти специальность по ключевым словам (например, «дизайн» или «программирование») без внешней настройки Elasticsearch.

В Data-as-Code архитектуре SurrealDB выступает как **производный кэш** для графовых запросов. Источником истины является Git-репозиторий. При потере БД — полное восстановление из Git через full sync webhook.

### Data Layer: Git + YAML/MD

- **Типовые `.yml` файлы** описывают данные о вузах, специальностях и группах ОП в структурированном формате, соответствующем SurrealDB-схеме.
- **`.md` файлы** содержат описания вузов в формате Markdown для rich-контента.
- **CI pipeline** валидирует JSON Schema при каждом PR — невалидные данные не попадают в систему.
- **Webhook** на push-события синхронизирует изменения в БД автоматически.

### Storage: MinIO

Self-hosted альтернатива AWS S3.

- **Зачем:** Хранение логотипов вузов, лицензий и фото кампусов.
- **Интеграция:** Бэкенд на Go выступает прокси: принимает файл, валидирует его (размер, формат) и перекладывает в MinIO, сохраняя в базе только ссылку.

## 5. Архитектурный ландшафт

Проект v2.0 строится на принципе **разделения контуров**:

1. **Контур данных (Git):** Структурированные YAML/MD файлы в Git-репозитории. PR-based workflow: diff → review → approve → merge → webhook → БД. Аутентификация — средствами Git-хостинга (SSH, PAT, SSO).

2. **Контур потребления (API):** Тонкая Go-прослойка, отвечающая за роутинг и графовые запросы к SurrealDB. Read-only JSON API для любого клиента (веб, мобильное приложение, Telegram-бот).

3. **Контур хранения:** SurrealDB (производный кэш графа) + MinIO (медиа-файлы). Оба восстановимы: БД — из Git, медиа — из бэкапов.

---

## 6. Безопасность через архитектуру

Переход на Data-as-Code — это в первую очередь решение по безопасности. Устранение веб-админки **отсекает целый класс атак**:

| Устранённый вектор                  | Как                             |
| ----------------------------------- | ------------------------------- |
| CSRF на admin endpoints             | Нет admin endpoints             |
| XSS через SSR-шаблоны               | Нет SSR-рендеринга              |
| OAuth hijacking / session fixation  | Нет OAuth / sessions            |
| Brute-force на логин                | Нет логина                      |
| CSS Injection через `safeCSS`       | Нет CSS-инъекции (нет шаблонов) |
| Cookie insecurity (`Secure: false`) | Нет cookies                     |

**Оставшиеся меры:** параметризованные SurrealQL-запросы, HMAC-SHA256 для webhook, валидация файлов (MIME, размер, UUID-имена), JSON Schema валидация в CI.

## 7. Этапы разработки

### Этап 0: GitOps Pipeline (Foundation)

_Реализуем полный цикл Data-as-Code: Git → CI → webhook → SurrealDB._

1. **Webhook handler** — приём push-событий, верификация подписи (HMAC-SHA256), парсинг изменённых файлов, upsert/delete в SurrealDB.

2. **JSON Schema** — валидация данных вузов, специальностей и групп ОП при каждом PR в CI.

3. **Full sync endpoint** — полная синхронизация всех данных из Git в БД (для первого деплоя или восстановления).

4. **Seed data** — наполнение data-репозитория первыми 5–10 вузами.

5. **Persistent storage** — переключение SurrealDB с `memory` на `file:`.

---

### Этап 1: Production Ready

_Доводим систему до состояния, пригодного для production._

1. **CORS middleware** — для будущего React SPA.

2. **Security headers** — helmet middleware (CSP, X-Frame-Options, nosniff).

3. **Rate limiting** — защита API и webhook от flood.

4. **Error handling** — generic ответы клиенту, structured logging на сервере (slog).

5. **Dockerfile** — multi-stage build, один бинарник в Alpine-контейнере.

6. **Reverse proxy** — Caddy с auto-TLS.

---

### Этап 2: Публичный фронтенд

_Запускаем интерфейс для абитуриентов._

1. **OpenAPI-спецификация** — формализация API-контракта, генерация TypeScript-типов.

2. **React SPA / Next.js** — каталог вузов, профиль вуза, каталог специальностей, калькулятор шансов.

3. **SEO** — SSR/ISR через Next.js для индексации страниц вузов.

4. **Telegram Bot MVP** — поиск, информация о вузах, калькулятор.

5. **Наполнение данными** — 50+ вузов через data-as-code pipeline.

---

### Этап 3: Масштабирование и фичи

_Масштабирование, продвинутые фичи, аналитика._

1. **API caching** — Redis/Valkey для горячих запросов.

2. **Monitoring** — Prometheus + Grafana.

3. **Data ingestion** — автоматический парсинг данных МОН РК → JSON → git commit.

4. **Mobile app** — React Native / Flutter.

5. **Архивные данные** — проходные баллы за прошлые годы, тренды.

## 8. Почему это «взлетит»?

Бизнес-ценность проекта в его **эффективности**. Пока конкуренты тратят деньги на огромные кластеры баз данных и команды фронтенд-разработчиков, мы строим систему, которая:

1. **Минимизирует поверхность атаки** — нет веб-админки, нет OAuth, нет сессий. Данные управляются через Git.

2. **Работает молниеносно** — тонкий API на Go + графовые запросы в SurrealDB, без SSR-оверхеда.

3. **Дёшева в поддержке** — все компоненты в Docker-контейнерах, данные в Git (бесплатный бэкап и аудит).

4. **Восстановима** — при потере БД полное восстановление из Git за < 1 минуту.

5. **Открыта для контрибьюций** — любой может отправить PR в data-репозиторий с данными о вузе, пройти review и увидеть изменения в API.

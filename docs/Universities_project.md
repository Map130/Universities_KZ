## 1. Контекст и Проблема (Зачем?)

В Казахстане ежегодно выпускается более 150 тысяч абитуриентов. Существующие порталы часто страдают от двух проблем:

1. **Информационный хаос:** Данные о проходных баллах, грантах и профильных предметах разбросаны по разным PDF-отчетам и не всегда актуальны.

2. **Технологическая отсталость:** В моменты пиковых нагрузок государственные ресурсы часто не справляются с трафиком.

**Цель проекта:** Создать отказоустойчивый сервис с удобной системой управления данными через Git (Data-as-Code), способный выдерживать высокие нагрузки на минимальных ресурсах.

---

## 2. Целевые данные (Что храним?)

Проект оперирует сетью связей, идеально подходящей под **графовую модель**:

- **Вузы (University):** Названия (RU/KZ/EN), локация, тип, описания, ссылки на логотипы (внешние).
- **Специальности (Specialty):** Код, название, описание.
- **Предметы ЕНТ (Subject):** Названия предметов.
- **Связи (The Core):**
  - **Offers (Вуз -> Специальность):** Гранты, стоимость, проходные баллы.
  - **Requires (Группа ОП -> Предметы):** Профильные предметы ЕНТ.

---

## 3. Архитектурная парадигма: Data-as-Code

Мы полностью отказались от классических админок в пользу паттерна **Data-as-Code**:

- **Данные** хранятся как структурированные **YAML** файлы в отдельном Git-репозитории.
- **Синхронизация** происходит через GitHub Webhook: при пуше бэкенд получает Tarball-архив репозитория, потоково парсит его и обновляет граф в SurrealDB.
- **Фронтенд** реализован на **Templ + HTMX**, обеспечивая высокую скорость работы (SSR) и интерактивность без тяжелых клиентских фреймворков.

---

## 4. Технологическая часть (Как?)

### Backend & Frontend: Go + Templ + HTMX

Бэкенд на Go выступает и как API, и как движок рендеринга.
- **SSR (Server-Side Rendering):** Использование Templ для типизированной генерации HTML.
- **Интерактивность:** HTMX для частичного обновления страниц (поиск, фильтры, калькулятор) без перезагрузки.
- **Webhook:** Приём push-событий из Git, верификация HMAC-SHA256, синхронизация данных.

### Database: SurrealDB

- **Graph:** Обход связей `university->offers->specialty` без сложных JOIN.
- **Document:** Хранение профилей вузов как JSON/YAML-подобных документов.
- **FTS:** Полнотекстовый поиск по специальностям и вузам из коробки.

---

## 5. Безопасность через архитектуру

Переход на Data-as-Code и SSR на Templ/HTMX отсекает большинство современных векторов атак:

| Устранённый вектор | Почему |
| ------------------ | ------ |
| CSRF / XSS         | Нет сессий, нет клиентского роутинга, типизированные шаблоны Templ |
| OAuth Hijacking    | Нет системы логина и OAuth |
| Admin API Attacks  | Нет административных API (все изменения через Git) |
| SQL Injection      | Использование параметризованных SurrealQL запросов |

## 7. Почему это эффективно?

1. **Скорость:** Минимальный Time-to-Interactive благодаря SSR и HTMX.
2. **Надежность:** При падении БД полная база восстанавливается из Git за секунды.
3. **Безопасность:** Минимальная поверхность атаки — нет админки, нет базы пользователей.
